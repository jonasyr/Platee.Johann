# v1.4.0 — Benutzerdefinierte Kategorien & Auto/On-Demand-Generierung

**Status:** approved design, ready for implementation planning
**Date:** 2026-09-07
**Issues:** #34, #35 (epic #39). Explicitly out of scope: #36, #38.

---

## 1. Problem

Two user complaints drive this work, both from the 2026-09 transcript:

1. **Speed.** Every entry generates all eight sections — eight GPT round-trips.
   Irrelevant when processing unattended; the dominant pain when the user sits in
   front of the machine waiting. *"Das dauert ziemlich lange … ätzend, wenn man
   direkt davor sitzt."*
2. **Freedom.** The set of sections is hard-coded across four layers, so adding a
   new kind of output (the user's example: a "Prompt zum Programmieren") is
   impossible without a code change. Prompt editing is additionally gated behind a
   shared admin password. *"So wie ihr das momentan macht mit den Passwörtern, das
   gefällt mir überhaupt nicht."*

## 2. Scope decision: additive, not a rewrite

Issue #34 as filed proposes replacing the eight fixed prompt fields with a generic
`CategoryDefinition` list, moving all section text into an `Entry.Sections`
dictionary at schema v4. Investigation on 2026-09-07 found this to be substantially
larger and riskier than the issue implies:

- **~290 references across 21 files** touch the eight section fields — including
  `SectionVisibility` / `SectionVisibilityViewModel`, `EmailRenderer`,
  `HtmlOverviewService` and `EntryMapper`, none of which #34 lists.
- **A hidden category-to-category dependency:** `GenerateEmailTextAsync` consumes
  `proseSummary` — another section's *output*, not the transcript.
  `ReprocessSectionAsync` falls back `ProseSummary ?? LongSummary ??
  EffectiveTranscript`. A flat category list with a single `Prompt` field cannot
  express this.
- **A data-loss path:** `JsonMigrator.Migrate` ends with an unconditional
  `dto.SchemaVersion = 3` and has no guard for a version newer than it knows.

**Decision (user, 2026-09-07): keep the eight built-ins as fixed fields; add
user-definable categories alongside them.** Users can edit built-in prompts, set
Auto/on-demand per section, and add unlimited personal or global categories. They
cannot rename or delete the built-ins in this release.

This is not merely a smaller change — it defuses the worst failure mode. See §4.3.

## 3. Data model

The organising principle: **unify at the read model, keep storage split.**

```csharp
// Platee.Johann.Application/Settings/CategoryDefinition.cs   (new)
public sealed record CategoryDefinition
{
    public required string Id     { get; init; }   // "custom.programmierung"
    public required string Name   { get; init; }
    public required string Prompt { get; init; }
    public CategoryScope Scope    { get; init; }   // Global | Personal
    public int Order              { get; init; }
    public int MaxTokens          { get; init; } = 20000;
}

public enum CategoryScope  { Global, Personal }
public enum GenerationMode { Auto, OnDemand }
```

### 3.1 Storage

| What | Where | Why |
| --- | --- | --- |
| Eight built-in prompts | `PromptSettings` (unchanged) | No migration of existing data |
| `IReadOnlyList<CategoryDefinition> CustomCategories` | `PromptSettings` (new, additive) | Shareable via the global `prompts.json` |

`CustomCategories` appears in **both** prompt files. `PromptSettingsLoader`
already loads global-with-local-fallback; it is extended to *merge* the two
category lists rather than pick one file: entries from the global `prompts.json`
carry `Scope = Global`, entries from the local file carry `Scope = Personal`, and
a personal category wins over a global one sharing its `Id`. `Scope` is therefore
derived from the file a category was read from, not stored redundantly inside it.

| `IReadOnlyDictionary<string, GenerationMode> SectionModes` | `AppSettings` (new) | **Personal per user** — nobody can slow down a colleague's pipeline |
| Generated custom text | `Entry.CustomSections` (new) | Additive; built-ins stay in their legacy fields |

### 3.2 Stable ids

Built-ins get reserved ids: `builtin.longSummary`, `builtin.proseSummary`,
`builtin.taskList`, `builtin.conversationNote`, `builtin.emailText`,
`builtin.stundenzettel`, `builtin.analog`.

`Title` and `Abstract` are **intrinsics**, not categories — they drive the entry
list UI and are never toggleable.

Custom ids are slugged and uniqued at creation time and are **never derived from
the mutable `Name`**, so renaming a category cannot orphan its generated text.

### 3.3 SectionCatalog

A new `SectionCatalog` projects built-ins + custom categories into one
`IReadOnlyList<SectionDescriptor>` ordered by `Order`. This is the single place
the UI and the pipeline ask "what sections exist?", so the split storage never
leaks into consumers.

### 3.4 Default generation modes

A one-time migration seeds:

- **Auto:** `longSummary`, `proseSummary`, `taskList`, `conversationNote` (four —
  the user's "vier oder fünf")
- **OnDemand:** `stundenzettel`, `analog`
- **E-Mail:** unchanged; already on-demand-only today
- **New custom categories:** default to `OnDemand`

This is a visible behaviour change. **It ships behind a one-time first-run prompt**
(user decision, 2026-09-07) that shows which sections moved to on-demand and offers to
keep the previous always-generate-everything behaviour. It must also be reversible in
settings afterwards and called out in the release notes.

## 4. Persistence

`Entry` gains `IReadOnlyDictionary<string,string> CustomSections`; `SchemaVersion`
goes to 4.

### 4.1 Version stamping

Entries are stamped `schemaVersion: 4` unconditionally.

An earlier draft proposed stamping v3 until an entry actually carried custom sections,
described as a data-safety measure. **That was wrong and has been removed.** It protects
only entries *without* custom sections — which have nothing to lose — while entries *with*
them are v4 either way. v1.3.2's migrator additionally branches only on `version < 2`, so
it treats v4 and v3 identically. The mechanism bought file-churn hygiene, not safety, at
the cost of a conditional in the serialisation path.

### 4.2 Migrator fixes

Both are genuine bug fixes and stay:

- Add `[JsonExtensionData] Dictionary<string, JsonElement>` to `EntryDto` so unknown
  fields round-trip. This is the real forward-compat fix, effective from v5 onward.
- Remove `JsonMigrator`'s unconditional `dto.SchemaVersion = 3`, which today silently
  **downgrades** the stamp on anything newer than it knows.

### 4.3 Mixed-version exposure (resolved)

**Confirmed by the user, 2026-09-07: entry directories are user-local and will stay that
way. Only `prompts.json` is shared on `Z:`.** No colleague's client ever reads or re-saves
another user's entry JSON, so the cross-user data-loss path described in earlier drafts
does not exist.

One residual case remains: the *same* user rolling back to v1.3.2 (a manual `Setup.exe`
reinstall, given this project's update history) would read their own v4 entries with a
client that drops `customSections` on re-save. `[JsonExtensionData]` cannot fix this
retroactively. Accepted — the loss is limited to custom sections, since the eight
built-ins remain in their legacy fields.

The live cross-version concern is therefore **`prompts.json`, not entries**: a v1.3.2
client must still parse a `prompts.json` that a v1.4.0 client wrote with a
`customCategories` key. It is an additive key and should be ignored, but this must be
verified manually against the real share.

## 5. Generation pipeline

One new generator method; the nine existing ones stay:

```csharp
Task<string?> GenerateCustomSectionAsync(
    CategoryDefinition cat, string transcript, CancellationToken ct);
```

`BuildSystemPrompt()` is reused unchanged, so custom categories inherit the
Korrekturliste for free.

### 5.1 Id-keyed dispatch

`ReprocessSectionAsync(entry, "Zusammenfassung")` currently switches on German
display strings passed as XAML `CommandParameter`. Two of those names are already
semantically inverted (`"Zusammenfassung"` → `LongSummary`, `"Ausführliche
Zusammenfassung"` → `ProseSummary`). Replace with:

```csharp
Task<Entry> GenerateSectionAsync(
    Entry entry, string sectionId, IProgress<ProcessingProgress>?, CancellationToken);
```

A single `SectionIdMap` translates legacy German strings → ids at the one call
site. `ReprocessSectionAsync` remains as a thin `[Obsolete]` delegate for one
release so the XAML bindings migrate separately.

### 5.2 Mode filtering

`GenerateSummariesAsync` consults `SectionModes`: only `Auto` built-ins fire, plus
`Auto` custom categories, still in parallel. E-Mail keeps its `ProseSummary`-derived
input — because built-ins are untouched, that dependency needs no generic
modelling.

### 5.3 Double-generation guard

`ConcurrentDictionary<(string JobId, string SectionId), Task<Entry>>` in the
processor: a second click awaits the first task rather than spending a second GPT
call. A `CanExecute` flag in the UI is **not** sufficient and must not be treated
as satisfying this requirement — it needs a concurrent test.

### 5.4 Regeneration

`RegenerateFromTranscriptAsync` regenerates auto sections plus any
*already-populated* on-demand sections, and does not newly generate empty ones.

## 6. UI

- **Detail pane:** the eight hand-written panels stay. One `ItemsControl` is added
  beneath them for custom sections, plus a placeholder row (name + „Generieren"
  button + busy state) for any un-generated on-demand section. This `DataTemplate`
  is where #38's Markdown rendering later lands — build it once.
- **`SectionVisibilityViewModel`** hard-codes eight `[ObservableProperty]` bools
  and a positional 8-argument `ToSectionVisibility()`. Add a parallel
  `IReadOnlyDictionary<string,bool>` for custom ids rather than reshaping the
  positional record, which all three renderers consume.
- **Settings:** new „Kategorien" section — add / duplicate / delete / reorder,
  scope toggle, prompt editor, and an Auto / „Auf Knopfdruck" toggle per section
  covering built-ins and custom alike.
- **Renderers:** `HtmlRenderer`, `PdfRenderer` and `HtmlOverviewService` all iterate the
  eight fixed fields and would otherwise never emit custom sections, breaking the
  "appears in the exported HTML and PDF" criterion. Add two optional `init` members to
  `RenderOptions` (`CustomSectionNames`, `CustomSectionVisibility`, both defaulting to
  empty so existing callers compile unchanged) and one append loop per renderer. Custom
  section text is user content and must go through the **same** encoder as built-in
  sections — a second escaping path would reopen the XSS hole closed in `acfd293`.

- **Password removal:** `SettingsViewModel` (16 refs), `SettingsView.xaml` (15),
  `AdminPasswordDialog.xaml` + `.xaml.cs`, `MainViewModel` (2), and delete
  `SettingsViewModelAdminTests.cs` (18). Independent of the category model.

## 7. Risks

| # | Risk | Mitigation |
| --- | --- | --- |
| 1 | ~~Custom sections dropped by a v1.3.x client re-saving a shared entry~~ | **Resolved** — entries are user-local (confirmed 2026-09-07). Residual: same-user rollback to v1.3.2 loses custom sections only; accepted |
| 2 | New Auto defaults surprise users | **First-run prompt** showing what changed (user decision 2026-09-07) + release-note callout + reversible in settings |
| 3 | **(now the top cross-version risk)** Global `prompts.json` change breaks older clients reading the same Z: file | `CustomCategories` is additive; old clients ignore it. **Manually verify a v1.3.2 client parses a v1.4.0-written prompts.json on the real share** |
| 4 | Id collisions between global and personal categories | Personal wins on `Id`; ids slugged + uniqued, never derived from `Name` |
| 5 | Double-generation burning GPT calls | Task-coalescing dictionary + concurrent test (§5.3) |
| 6 | Reordering fights the fixed built-in panels | Custom-section ordering only in v1.4.0 |
| 7 | `SectionVisibility` positional-record churn | Additive dictionary, don't reshape |
| 8 | A prompt missing `{transcript}` silently produces garbage | Validate on save; warn in the editor |
| 9 | Deleting a category orphans generated text | Keep the data; render orphans read-only under „Nicht mehr konfiguriert" |
| 10 | Scope creep from #36 | #36 explicitly out of scope |

## 8. Testing

The existing 44-file suite is the safety net; `EntryProcessingServiceTests` (7) and
`JsonMigratorTests` (7) are extended rather than replaced.

Required before merge:

- Custom-category merge precedence (personal beats global on `Id`)
- v3→v4 round-trip **and** the v3-stays-v3 rule (§4.1)
- Auto-only filtering: 4 auto categories issue 4 section calls, not 8
- Single-section generate + merge + persist
- Concurrent double-click coalescing issues exactly one LLM call
- Prompt-placeholder validation
- Orphaned-category rendering

## 10. Resolved questions

Both settled by the user on 2026-09-07:

1. **New Auto defaults ship behind a first-run prompt**, not silently. The prompt shows
   what changed and offers to retain the previous behaviour. See §3.4.
2. **Entry directories are user-local and will remain so.** Only `prompts.json` is shared.
   This resolves risk 1 and makes `prompts.json` compatibility the only live cross-version
   concern. See §4.3.
